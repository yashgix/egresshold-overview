Check what leaves the machine before it leaves

A fail-closed boundary for coding-agent clients. Every outgoing upload is scanned for secrets and personal details, and an upload that cannot be checked is not sent.

Overview only. Reproduction steps, affected code paths and the full evidence are kept in a private repository.

The problem class

Text can leave the machine before anything checks it

Coding-agent clients upload text that an agent wrote: notes, comments, searches. Agents quote what they have seen, including keys, tokens and personal details. A check that covers only some upload paths, or that quietly lets text through when it fails, leaves a gap. From reading the client's source, in the default mode the person does not review each upload, so they cannot catch it either. This was not tested.

The service may check content on its side. That was not tested, because testing it would mean sending data to the service. The real exposure may therefore be smaller than the client alone suggests.

Defensive approach

Check at the one place everything leaves, and fail closed

  • One choke point. Every guarded upload already passes through one request function, so one check there covers all of them, including ones added later. Login and other non-upload requests are left alone.
  • Fail closed. If the scan errors, times out or cannot load its rules, nothing is sent. A delayed note can be recovered. A leaked key cannot.
  • Reuse proven rules. The scan ports the default rules of a widely used open-source secret scanner and checks the port against the real tool.
  • Hold, do not retry. A blocked queued item is kept locally and never retried, so it cannot delay the items behind it.

Limits
The scanner is a floor, not a guarantee
    

  • It misses text that is split, encoded in base64 or hex, stacked in an unsupported order, or written as a generic password in prose.
    • 

  • No detection rate is claimed. A licensed real-world measurement has not been run.
    • 

  • About 1.6% of 1,000 ordinary public posts were flagged. The flags were not adjudicated, so this is a flag rate and not a false-positive rate. A false positive blocks an upload.
    • 

  • The service's own check, real agent notes and one importer path were not exercised end to end.

Implementation decisions
Why it works this way
Fail closed
A scan error, timeout or bad rules file blocks the upload.
Port, do not invent
The default rules of the reference scanner are widely used, and a port can be tested against the real tool.
Scan in a worker thread
A slow regular expression cannot be interrupted on the main thread. A worker can be terminated at the deadline.
Bound the walk first
Size and depth limits run before the deadline, so a hostile or huge body cannot stall the check.
Scan what actually leaves
The check covers link parts, nested values, object keys, and percent-decoded and JSON-unescaped views.
The uploader cannot opt out
An allow marker inside the uploaded text does not switch the check off, because the uploader controls that text.
Hold, do not retry
A blocked queued item moves to a local folder, is listed in the status view, and never delays the items behind it.

Limitations
What this does not show
    

  • The scanner is a floor. It does not catch split, base64 or hex forms, stacked encodings, or generic passwords in prose.
    • 

  • The service's own check was not tested, so the real effect on users is unknown.
    • 

  • The false-positive sample is public question-and-answer text, not real agent notes.
    • 

  • One importer path's own synchronous check sits outside the 3-second deadline.
    • 

  • A very long note is blocked when its scan passes 3 seconds or it exceeds 1 MB of text.
    • 

  • Some differences from the reference scanner remain: no base64 or hex decoding, and quantifiers count UTF-16 units on emoji.
